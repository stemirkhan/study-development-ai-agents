## Четыре исполняющих компонента

1. `ModelClient` выполняет ровно один обмен через детерминированный
   `ScriptedTransport`, преобразует ответ поставщика в
   `FinalAnswer | ToolCall` и не исполняет `tool`.
2. `AgentLoop` хранит `context`, проверяет список разрешённых функций и
   аргументы `tool call`, координирует вызов разрешённой функции и ограничивает
   число обращений к LLM.
3. `Workflow` задаёт фиксированный порядок: проверить вход, выполнить заранее
   выбранный шаг Agent, проверить бизнес-инвариант результата.
4. `DistributedExecutor` размещает уже выбранную асинхронную операцию,
   выполняет одну попытку и не интерпретирует запрос пользователя.

`ScriptedTransport` и `get_weather` — детерминированные подмены внешних
зависимостей, а не дополнительные компоненты исполнения.

## Сквозная трасса

Для запроса «Нужен ли сегодня зонт в Казани?»:

1. `Workflow` проверяет вход и выбирает известный шаг рекомендации.
2. `DistributedExecutor` запускает первую и единственную попытку шага.
3. `AgentLoop` через `ModelClient` получает недоверенный
   `ToolCall(get_weather)`.
4. `AgentLoop` проверяет точное имя и схему `{city: str}`, после чего вызывает
   `get_weather`.
5. Результат `tool` добавляется в `context`; второе обращение к LLM возвращает
   финальный ответ.
6. Результат поднимается через `DistributedExecutor` и `Workflow`
   пользователю.

Демонстрация печатает 18 детерминированных событий трассы и итоговые счётчики:
`model_calls=2`, `tool_calls=1`.

## Инварианты и отказные режимы

- `tool call` не даёт полномочий: неизвестное имя, лишнее поле, пустой либо
  неверно типизированный `city` отклоняются до побочного эффекта.
- Новый `tool call` на последнем доступном шаге LLM не исполняется: не осталось
  шага, который увидит результат.
- Повторный `call_id` внутри одного запуска отклоняется до второго исполнения
  `tool`.
- `ModelClientError` проходит через `AgentLoop` и `DistributedExecutor` без
  изменения; `Workflow` добавляет имя шага через `WorkflowStepFailed` и
  сохраняет исходную причину.
- `CancelledError` проходит через все четыре границы без преобразования в
  доменную ошибку.
- `DistributedExecutor` не повторяет операцию. Истёкший до старта монотонный
  `deadline` даёт `TaskDeadlineExceeded`; истечение после старта или потеря
  подтверждения даёт `AmbiguousCompletion`, потому что побочный эффект уже мог
  произойти.

## Проверки

Тесты разделены по наблюдаемому контракту:

- модульные: остановка цикла, порядок `context`, лимиты и передача ошибок;
- контрактные: варианты ответа `ModelClient` и детерминизм `get_weather`;
- интеграционные: точная сквозная трасса через четыре компонента;
- отказные и security: неизвестные `tool`, расхождение схемы, превышение
  крайнего срока, отмена, недоступный исполнитель и потеря подтверждения;
- тест свойств: полный детерминированный перебор коротких последовательностей
  `final/tool` проверяет верхние границы обращений к LLM и `tool`.

## Базовое решение и ограничения

Если погода требуется для каждого запроса, базовое решение проще:
`Workflow → get_weather → детерминированное форматирование`. Текущий Agent не
доказывает измеримого выигрыша над ним; пример нужен для изучения границ, а не
как рекомендация эксплуатационной архитектуры.

`DistributedExecutor` здесь — локальная модель одной попытки с внедряемыми
отказными сценариями, а не очередь или гарантия exactly-once. `deadline` —
абсолютное значение часов `time.monotonic`. В примере разрешён только
read-only `get_weather`: защита повторного `call_id` не заменяет
идемпотентность при новом id или перезапуске процесса. Нет потокового ответа,
SDK поставщика, полного движка JSON Schema, `checkpoint/replay` и
автоматических повторных попыток. Эти механизмы относятся к последующим темам.
Сопоставление с готовым framework на этом Gate намеренно отсутствует.
