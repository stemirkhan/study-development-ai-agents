# Практика 1.4: возможности и резервный маршрут

Практика относится к
[модулю 1, теме 1.4](../../docs/senior_ai_agent_engineer_2026.md#промпт-14-возможности-и-резервный-маршрут)
и продолжает
[теоретический конспект](../../notes/module_01_capability_fallback/module_01_capability_fallback.md).
Настоящих API и SDK здесь нет: профили, ответы и отказы заданы
детерминированно.

## Что реализовано

Неизменяемый реестр хранит конкретные маршруты и проверенные профили. Профиль
описывает доступные инструменты, строгую схему, входные и выходные типы данных,
лимиты контекста, обычный или потоковый режим, экспериментальные функции и
зрелость. Имя модели нигде не определяет возможности веткой `if`.

Маршрутизатор всегда выполняет операции в таком порядке:

```text
проверить каждый профиль → исключить несовместимые → ранжировать совместимые
```

Неизвестный профиль считается несовместимым. Если подходящего маршрута нет,
`NoCompatibleRoute` возвращает отчёты по всем кандидатам до обращения к
адаптеру. Ранжирование не получает несовместимые варианты и поэтому не может
сделать дешёвую модель допустимой.

Перед планированием `RoutingRequest` сопоставляет фактические инструменты,
схемы их аргументов и схему итогового ответа с объявленными требованиями. Поле
`$schema` каждой схемы обязано точно совпасть с требуемым диалектом: вызывающий
слой не может получить допуск, недодекларировав `pattern`, `oneOf` или другой
используемый элемент вложенной схемы.

## Сквозная трасса

Демонстрация моделирует шаг агента, которому нужны два инструмента, изображение
на входе, строгая схема, контекст `52k + 4k` и
`reasoning_budget:v1`.

```text
BUILDING_CHANGE_PLAN
└── проверка реестра 2026-08-12.3
    ├── primary-a  → совместим → выбран первым
    ├── cheap-c    → нет инструмента, изображения, строгой схемы и функции
    └── fallback-b → совместим

primary-a: доказанный отказ до попытки и побочного эффекта
└── fallback-b: новый ModelRequest с его model
    ├── тот же request_id, messages, tools и response_format
    ├── тот же абсолютный Deadline
    └── завершённый структурированный ответ
```

Типизированный `EffectFreeRouteFailure` вместе с `EffectFreeEvidence` и
проверяемой ссылкой `proof_ref` является явным доказательством для резервного
выбора. Метаданные ответа поставщика противоречат утверждению
`BEFORE_ATTEMPT` и отклоняются. Обычный `ModelUnavailable`, отмена или
`ModelStreamInterrupted` не перехватываются: они не доказывают отсутствие
серверного побочного эффекта и не разрешают новую генерацию.

Исполнитель проверяет крайний срок до и после планирования, передаёт тот же
`Deadline` каждой попытке и сам ограничивает ожидание клиента. Поэтому адаптер,
игнорирующий `ModelAttempt.deadline`, отменяется координатором, а его поздний
ответ не принимается. Успешный ответ дополнительно сверяется по `request_id`,
поставщику и идентификатору модели выбранного маршрута. Если поставщик
возвращает канонический снимок вместо запрошенного псевдонима, допустимые
идентификаторы задаются явно в `accepted_response_models`.

Если совместимые варианты исчерпаны, `NoCompatibleRoute` сохраняет не только
отчёты и исключённые маршруты, но и уже выполненные попытки, причины и
`proof_ref`. Неуспешный резервный выбор поэтому остаётся воспроизводимым по
журналу.

Причинная связь с агентом:

```text
несовместимый профиль → нет завершённого решения модели
→ нет проверенного предложения вызвать инструмент
→ полномочия на инструмент не выдаются → состояние репозитория не меняется
```

Выбор совместимой модели также не выдаёт полномочий инструменту. Завершённое
предложение всё равно должно пройти проверку схемы, списка разрешений и
политики побочного эффекта на отдельной границе исполнения.

## Запуск

```bash
uv run --frozen python -m \
  lessons.module_01_capability_fallback.implementation.demo

uv run --frozen pytest -q \
  lessons/module_01_capability_fallback/tests \
  lessons/module_01_provider_contract/tests
```

`test_properties.py` исчерпывающе перебирает 8192 сочетания тринадцати
признаков. Для каждого сочетания кандидат с лучшим приоритетом выбирается
только тогда, когда удовлетворяет всем требованиям. В остальных случаях
побеждает совместимый контрольный маршрут, а клиенты не вызываются.

## Границы доказательства

- Реестр статический; проверка не доказывает актуальные права учётной записи,
  доступность сервиса или качество ответа.
- Размер контекста задаётся готовыми бюджетами без токенизатора.
- Предварительная проверка JSON Schema обходит известные контейнеры вложенных
  схем и сверяет диалект и используемые ключевые слова, но не заменяет полный
  валидатор схемы и ограничения конкретного поставщика.
- Независимые поля не выражают все ограничения сочетаний возможностей
  промышленных API.
- Резервный исполнитель поддерживает только непотоковый `complete`. Возможность
  потокового режима участвует в планировании, но склеивание потоков разных
  моделей намеренно не реализовано.
- Детерминированные имитации доказывают порядок локальных решений и отсутствие
  скрытого вызова несовместимого клиента, но не поведение удалённого сервиса.
- `proof_ref` проверяется на структурную согласованность и сохраняется в
  журнале, но эта практика не подключает внешнее хранилище доказательств
  работоспособности или результатов сверки.
