# ReAct (Reasoning + Acting)

> **Статус:** архивный урок из предыдущего плана. Используйте его как
> исторический baseline перед модулем 8 нового трека, но не как замену
> provider-native Tool Calling из модуля 2.

## Цель урока

После изучения материала вы будете понимать:

- что такое паттерн ReAct;
- зачем LLM нужны внешние инструменты;
- чем отличаются Reasoning, Action и Observation;
- как JSON-ответ модели превращается в вызов Python-функции;
- как результат инструмента возвращается в контекст модели;
- зачем агенту ограничение количества шагов.

В этом уроке агент реализован на чистом Python с использованием OpenAI SDK.
LangChain и другие агентные фреймворки не используются.

## Что такое ReAct

ReAct расшифровывается как **Reasoning + Acting** — «рассуждение и действие».

Это паттерн построения AI-агентов, в котором языковая модель работает
итеративно:

1. Анализирует текущую задачу и доступный контекст.
2. Выбирает следующее действие.
3. Запрашивает вызов инструмента.
4. Получает результат инструмента — Observation.
5. Анализирует обновлённый контекст.
6. Вызывает следующий инструмент или формирует финальный ответ.

Общая схема:

```text
Вопрос пользователя
        ↓
LLM выбирает следующее действие
        ↓
Action: имя инструмента и аргументы
        ↓
Python вызывает инструмент
        ↓
Observation: результат инструмента
        ↓
Observation добавляется в контекст
        ↓
Следующий вызов LLM
        ↓
Новый Action или Final Answer
```

Ключевая особенность ReAct — модель не обязана сразу отвечать пользователю.
Сначала она может получить недостающую информацию или выполнить точное
вычисление.

## Три основных элемента ReAct

### 1. Reasoning

Модель анализирует задачу и решает, что делать дальше:

- ответить самостоятельно;
- выполнить вычисление;
- найти информацию;
- использовать результат предыдущего инструмента;
- завершить работу.

Reasoning не обязательно означает публикацию полной внутренней цепочки
рассуждений. В нашей реализации модель возвращает только результат своего
решения: JSON с вызовом инструмента или финальным ответом.

### 2. Action

Action — структурированное описание следующего действия.

Например:

```json
{
  "action": "tool",
  "tool_name": "calculator",
  "arguments": {
    "expression": "(17 + 5) * 3"
  }
}
```

Этот JSON ещё не вызывает функцию. Это обычный текст, сгенерированный LLM.

### 3. Observation

Observation — результат выполнения действия:

```json
{
  "tool_name": "calculator",
  "result": "66"
}
```

Python добавляет Observation в историю сообщений. На следующем шаге модель
видит результат и может использовать его при подготовке ответа.

## Кто за что отвечает

| Компонент | Ответственность |
|---|---|
| Пользователь | Формулирует исходную задачу |
| LLM | Выбирает действие и генерирует JSON |
| Python-оркестратор | Проверяет JSON, управляет циклом и вызывает функции |
| Инструмент | Выполняет конкретную операцию |
| Observation | Передаёт результат инструмента обратно модели |

LLM не запускает Python-код напрямую. Реальное выполнение контролируется
оркестратором.

## Инструменты нашего агента

Агенту доступны два инструмента.

### Симулированный поиск

Функция `web_search()` имитирует поиск в интернете:

```python
def web_search(query: str) -> str:
    ...
```

Она не отправляет сетевые запросы, а ищет ответ в небольшой локальной базе.
Это позволяет изучить агентный цикл без подключения настоящего поискового API.

### Калькулятор

Функция `calculator()` вычисляет арифметические выражения:

```python
calculator("(17 + 5) * 3")
```

Результат:

```text
66
```

Калькулятор не использует `eval()`. Выражение разбирается стандартным модулем
`ast`, поэтому произвольный Python-код выполнить нельзя.

## Как LLM узнаёт об инструментах

Модель не читает файл `tools.py` и ничего не знает о Python-функциях
автоматически.

Доступные инструменты описаны в системном промпте:

```text
Доступные инструменты:
1. web_search с аргументами {"query": "строка"}.
2. calculator с аргументами {"expression": "арифметическое выражение"}.
```

Промпт также определяет формат ответа:

```json
{
  "action": "tool",
  "tool_name": "web_search",
  "arguments": {
    "query": "что найти"
  }
}
```

Если инструменты больше не нужны, модель должна вернуть:

```json
{
  "action": "final",
  "answer": "итоговый ответ пользователю"
}
```

## Как JSON превращается в вызов функции

Рассмотрим ответ модели:

```json
{
  "action": "tool",
  "tool_name": "calculator",
  "arguments": {
    "expression": "(17 + 5) * 3"
  }
}
```

### Шаг 1. Парсинг JSON

Python преобразует строку в словарь:

```python
payload = json.loads(raw_response)
```

Получается:

```python
{
    "action": "tool",
    "tool_name": "calculator",
    "arguments": {
        "expression": "(17 + 5) * 3",
    },
}
```

### Шаг 2. Создание объекта ToolCall

После проверки полей создаётся объект:

```python
ToolCall(
    name="calculator",
    arguments={"expression": "(17 + 5) * 3"},
)
```

### Шаг 3. Поиск функции в реестре

Разрешённые функции хранятся в словаре:

```python
TOOLS = {
    "web_search": web_search,
    "calculator": calculator,
}
```

Python получает функцию по имени:

```python
tool = TOOLS["calculator"]
```

Переменная `tool` теперь содержит ссылку на функцию `calculator`.

### Шаг 4. Вызов функции

Функция вызывается следующей строкой:

```python
result = tool(**tool_call.arguments)
```

Оператор `**` распаковывает словарь в именованные аргументы. Поэтому вызов
эквивалентен следующему коду:

```python
result = calculator(expression="(17 + 5) * 3")
```

Именно на этом шаге происходит настоящее выполнение инструмента.

## Пошаговый разбор примера

Вопрос:

```text
Что такое ReAct и сколько будет (17 + 5) * 3?
```

### Первый вызов LLM

Модель выбирает калькулятор:

```json
{
  "action": "tool",
  "tool_name": "calculator",
  "arguments": {
    "expression": "(17 + 5) * 3"
  }
}
```

### Выполнение инструмента

Python вызывает:

```python
calculator(expression="(17 + 5) * 3")
```

Калькулятор возвращает:

```text
66
```

### Добавление Observation

В историю сообщений добавляется:

```text
Observation: {"tool_name": "calculator", "result": "66"}
```

### Второй вызов LLM

Модель уже видит точный результат и возвращает:

```json
{
  "action": "final",
  "answer": "ReAct чередует рассуждения и действия. Результат вычисления: 66."
}
```

После `action: final` цикл завершается.

## Почему поиск не был вызван

Модель уже знала определение ReAct из своих параметрических знаний. Системный
промпт не требовал обязательно использовать поиск для каждого информационного
вопроса.

Для вычислений в промпте задано отдельное правило:

```text
Для вычислений используй calculator.
```

Поэтому модель вызвала калькулятор, но не вызвала поиск.

Выбор инструмента определяется:

- системным промптом;
- описанием инструментов;
- вопросом пользователя;
- текущей историей сообщений;
- решением модели на конкретном шаге.

## Основной ReAct-цикл

Упрощённый псевдокод агента:

```python
messages = [{"role": "user", "content": question}]

for step in range(max_steps):
    raw_response = call_llm(messages)
    action = parse_llm_response(raw_response)

    if action является FinalAnswer:
        return action.answer

    observation = execute_tool(action)

    messages.append({
        "role": "user",
        "content": f"Observation: {observation}",
    })

return "Достигнут лимит шагов"
```

Главная идея цикла:

```text
LLM → Action → Python → Tool → Observation → LLM
```

## Зачем нужен `max_steps`

Модель может:

- многократно вызывать один и тот же инструмент;
- возвращать некорректный JSON;
- не переходить к финальному ответу;
- зациклиться между несколькими действиями.

Поэтому цикл ограничен:

```python
for step in range(1, max_steps + 1):
    ...
```

Если финальный ответ не получен, агент останавливается:

```text
Агент остановлен после 6 шагов:
модель не сформировала финальный ответ.
```

Ограничение шагов защищает от:

- бесконечного цикла;
- лишних API-запросов;
- неконтролируемых расходов;
- слишком долгого выполнения.

## Обработка ошибок

В реализации предусмотрено несколько уровней защиты.

### Некорректный JSON

Если модель вернула невалидный JSON, ошибка добавляется как Observation.
Модель получает возможность исправить формат на следующем шаге.

### Неизвестный инструмент

Если модель запросила инструмент, которого нет в `TOOLS`, функция не вызывается.
В контекст возвращается сообщение со списком доступных инструментов.

### Неправильные аргументы

Если аргументы не соответствуют сигнатуре функции, ошибка превращается в
Observation.

### Ошибка инструмента

Деление на ноль, неправильное выражение и другие ожидаемые ошибки передаются
модели, а не завершают процесс аварийно.

### Ограничение арифметики

Калькулятор ограничивает:

- длину выражения;
- доступные математические операции;
- показатель степени;
- максимальный размер результата.

## ReAct и нативный Tool Calling

В этом уроке используется ручной JSON-протокол:

1. Промпт просит модель вернуть JSON.
2. Python вызывает `json.loads()`.
3. Код самостоятельно находит и вызывает функцию.

Современные LLM API также поддерживают нативный tool calling, при котором
описание инструментов передаётся через специальные параметры SDK.

Ручной вариант полезен для обучения, потому что явно показывает:

- откуда появляется имя инструмента;
- как проверяются аргументы;
- где вызывается Python-функция;
- как Observation попадает обратно в контекст;
- как устроен агентный цикл внутри фреймворков.

## Когда ReAct полезен

ReAct подходит для задач, где одного ответа LLM недостаточно:

- поиск актуальной информации;
- вычисления;
- работа с базой данных;
- чтение файлов;
- вызов внешнего API;
- проверка фактов;
- выполнение нескольких зависимых действий;
- подготовка ответа на основе результатов инструментов.

## Ограничения ReAct

ReAct не гарантирует идеального поведения:

- модель может выбрать неправильный инструмент;
- аргументы могут быть некорректными;
- результат инструмента может быть неполным;
- модель может проигнорировать Observation;
- количество шагов увеличивает задержку и стоимость;
- содержимое внешнего инструмента может быть недоверенным.

В production-системах дополнительно применяют:

- строгие JSON-схемы;
- нативный tool calling;
- таймауты инструментов;
- логирование каждого шага;
- контроль стоимости;
- проверку прав доступа;
- защиту от prompt injection;
- ограничение размера Observation;
- повторные попытки для временных ошибок;
- подтверждение опасных действий пользователем.

## Главные выводы

1. ReAct чередует выбор действия и анализ результата.
2. LLM не вызывает Python-функцию напрямую.
3. LLM возвращает структурированное описание действия.
4. Python проверяет действие и управляет выполнением.
5. `TOOLS` является списком разрешённых функций.
6. Observation возвращает результат инструмента в контекст.
7. Цикл продолжается до `final` или достижения `max_steps`.
8. Детерминированные задачи лучше передавать специализированным инструментам.
