# Возможности и резервный маршрут

> [Основной план, модуль 01](../../docs/senior_ai_agent_engineer_2026.md)

## Краткое содержание

Резервный маршрут — это не «следующая LLM в списке», а повторный выбор только
среди вариантов, которые сохраняют смысл текущего шага Agent. Маршрутизатор
сначала проверяет доступные tool, строгую схему, типы входных данных, размер
context, потоковую выдачу и явно включаемые экспериментальные возможности.
Лишь после этого совместимые маршруты ранжируются по работоспособности,
задержке и стоимости. Если ни один вариант не подходит, корректный результат —
ошибка `NoCompatibleRoute`, а не молчаливое удаление tool или ослабление схемы.

## Ключевые понятия

| Понятие | Смысл |
|---|---|
| Маршрут | `ModelRoute`: устойчивый идентификатор, адаптер и конкретный профиль возможностей |
| Профиль возможностей | `CapabilityProfile`: проверенные свойства конкретной конфигурации поставщика |
| Требования | `CapabilityRequirements`: обязательные условия одного решения LLM, сформированные до выбора маршрута |
| Обязательное требование | Условие корректности, которое нельзя ослабить ради доступности |
| Критерий предпочтения | Работоспособность, задержка, стоимость или оценка качества среди уже совместимых маршрутов |
| Отчёт о совместимости | `CompatibilityReport`: результат проверки со всеми причинами отказа и источником сведений |
| Нет подходящего маршрута | `NoCompatibleRoute`: отказ до вызова LLM, если ни один маршрут не удовлетворяет требованиям |
| Явное ослабление | Новое решение приложения с изменёнными требованиями и записью аудита |

Возможности относятся не только к `model_name`, а ко всей эффективной
конфигурации:

```text
поставщик + версия LLM + вариант API + параметры/заголовки + регион/учётная запись
```

Изменяемый псевдоним со временем может начать указывать на другую версию LLM.
Одна и та же LLM может иметь разные возможности в OpenAI Responses и OpenAI Realtime
или устаревшей точке API. Заголовок бета-функции, права учётной записи и регион
тоже меняют фактический контракт.

## Основные идеи

### Проблема: доступность без подмены смысла

Пусть Agent должен разобрать снимок экрана, вернуть результат по строгой схеме
`change_plan/v1` и при необходимости предложить `propose_patch`. Основной
маршрут недоступен. Дешёвый резервный вариант принимает только текст,
генерирует JSON без гарантии соответствия схеме и не знает `propose_patch`.

Если маршрутизатор удалит изображение, tool или строгую схему и всё же вернёт
обычный `ModelResponse`, Agent продолжит работу в ложном состоянии. Вызов LLM
снаружи выглядит успешным, хотя пространство допустимых решений уже
изменилось. Это не ухудшение задержки или качества, а подмена задачи.

Инвариант маршрутизации:

```text
возможности(выбранный_маршрут) удовлетворяют всем обязательным требованиям
```

`unknown` не означает `supported`. Если метаданных недостаточно, маршрут
считается несовместимым до успешного контрольного запроса или обновления
описания возможностей.

### Требования и профили возможностей — разные модели данных

`CapabilityProfile` описывает, что конкретный маршрут технически способен
предложить. `CapabilityRequirements` описывает, что требуется конкретному
переходу состояния Agent. Один маршрут может подходить для текстовой
классификации и не подходить для шага с изображением и tool.

Минимальное отношение совместимости:

```text
requirements.tools              ⊆ profile.available_tools
requirements.input_modalities   ⊆ profile.input_modalities
requirements.output_modalities  ⊆ profile.output_modalities
requirements.min_input_tokens   ≤ profile.max_input_tokens
requirements.min_output_tokens  ≤ profile.max_output_tokens
если profile.max_total_tokens задан:
  requirements.min_input_tokens + requirements.min_output_tokens
    ≤ profile.max_total_tokens
requirements.schema.mode        ∈ profile.schema_modes
schema_preflight(requirements.schema, profile.schema_dialect) = compatible
requirements.stream_mode        ∈ profile.stream_modes
requirements.experimental       ⊆ profile.experimental_features
profile.maturity                ∈ requirements.allowed_maturity
```

Входной бюджет включает системный prompt, историю, определения и результаты
tool, а также входные данные разных типов. Резерв ответа проверяется отдельно.
Если поставщик дополнительно задаёт общее окно, проверяется и сумма входного
бюджета с резервом ответа. Большое входное окно само по себе не гарантирует,
что LLM сможет вернуть ответ нужной длины. Одного `len(user_text)` недостаточно.
Типы входных и выходных данных хранятся раздельно: приём изображения не
означает умение создать изображение.

Метка `strict` — необходимое, но не достаточное условие. Поставщики
поддерживают разные подмножества и диалекты JSON Schema. Поэтому реестр хранит
диалект и ограничения, а схема проходит предварительную проверку для
конкретного маршрута. Неизвестное ключевое слово или неподдержанная комбинация
дают типизированную причину отказа до вызова LLM.

Поддержка tool тоже не сводится к `supports_tools=True`. Нужны как минимум
точные идентификаторы tool, место выполнения (`client` или `server`), режим
схемы и ограничения параллельных вызовов. Наличие tool в профиле означает лишь
способность LLM предложить вызов; полномочий на выполнение оно не выдаёт.

### Независимые признаки могут вводить в заблуждение

Поддержка tool и строгого структурированного ответа по отдельности не
доказывает, что их можно использовать вместе. Реальный профиль должен хранить
поддерживаемые режимы и ограничения:

```text
mode: streaming + client_tools + strict_tool_schema
mode: non_streaming + structured_final_response
constraint: structured_final_response + built_in_tools = preview_only
```

В небольшой практике 1.4 начнём с явных полей и отдельного списка
версионированных экспериментальных возможностей. Ограничение такой модели
нужно зафиксировать: промышленный реестр обязан описывать существенные
комбинации, а не вычислять их как произведение независимых булевых признаков.

### Поток выполнения

![Agent формирует обязательные требования, маршрутизатор исключает несовместимые варианты, а при оборванном потоке или неизвестном побочном эффекте требует отдельного решения](diagrams/capability-routing.png)

1. Состояние Agent и разрешённый набор tool порождают обязательные требования.
2. Маршрутизатор читает неизменяемый снимок реестра и строит
   `CompatibilityReport` для каждого возможного маршрута.
3. Проверка совместимости исключает варианты с любым несоответствием до вызова
   адаптера.
4. Политика ранжирования сравнивает только совместимые маршруты по
   работоспособности, задержке, стоимости или оценке качества.
5. Выбранный адаптер выполняет ровно один запрос к поставщику. Маршрутизация
   остаётся над `ModelClient`, а не скрывается внутри него.
6. Вызывающий слой может выбрать следующий совместимый маршрут под тем же
   общим крайним сроком и лимитами только при сбое, допускающем переключение:
   до первого принятого события потока **и** когда побочный эффект tool на
   стороне сервера заведомо невозможен либо сверка уже подтвердила его
   отсутствие.
7. После принятого события действует правило темы 1.3: нельзя неявно
   переключаться на другую LLM и склеивать части разных попыток. Наружу идёт
   `ModelStreamInterrupted`, а дальнейшее решение принимает вызывающий слой.
8. Завершённый `ModelResponse` возвращается Agent. Предложение вызвать tool ещё
   проходит проверку схемы, списка разрешённых tool и полномочий до побочного
   эффекта.

Отсутствие первого события говорит только о наблюдаемом потоке. Оно не
доказывает, что tool на стороне сервера не успел выполниться. Если состояние
побочного эффекта неизвестно, Agent переходит в состояние ожидания сверки;
автоматическое переключение запрещено. Ключ идемпотентности помогает сверить
или безопасно повторить уже известную операцию, но сам по себе не доказывает
эквивалентность нового решения LLM.

### Границы ответственности

| Компонент | Владеет | Не должен делать |
|---|---|---|
| Реестр | Профили, источник сведений, редакция, `verified_at` | Ранжировать, вызывать LLM или разрешать выполнение tool |
| Проверка совместимости | Сопоставление обязательных требований и точные причины отказа | Ослаблять требования ради доступности |
| Политика ранжирования | Порядок уже совместимых маршрутов | Делать несовместимый маршрут допустимым |
| Адаптер / `ModelClient` | Один запрос к поставщику и нормализация ответа | Скрыто менять LLM или выбирать резервный маршрут |
| Agent / приложение | Явное ослабление требований и переход состояния | Считать выбор маршрута полномочием на tool |
| Граница выполнения tool | Схема, список разрешений, полномочия, идемпотентность | Исполнять частичное или непроверенное предложение |

Маршрутизатор не изменяет шаблон запроса, независимый от маршрута. Поле
`ModelRequest.model` обязательно, поэтому после выбора строится новый
`ModelRequest(model=selected_route.model, ...)`. Значения `messages`, `tools`,
`response_format` и идентификатор запроса приложения остаются прежними. Резервный
маршрут B никогда не получает идентификатор LLM от маршрута A. Если для
переключения нужно удалить tool, сжать context, заменить изображение описанием
или перейти от строгой схемы к обычному тексту, это уже новое решение
приложения, новый запрос и отдельная запись аудита.

### Причинная связь с Agent

Несовместимая ветка:

```text
проверка совместимости отклоняет дешёвый резервный маршрут
→ Agent: BUILDING_CHANGE_PLAN → BLOCKED_BY_CAPABILITY
→ завершённого решения LLM нет
→ предложения вызвать tool и полномочий на выполнение нет
→ состояние репозитория не меняется
```

Совместимая ветка с предложением вызвать tool:

```text
совместимый резервный маршрут → завершённый ModelResponse
→ предложение LLM входит в состояние Agent
→ проверка схемы, списка tool и полномочий
→ только затем допустимый побочный эффект tool
```

Если завершённый ответ не содержит предложения вызвать tool, он просто входит
в состояние Agent; ветки проверки полномочий и побочного эффекта нет.

Маршрутизация сохраняет возможность получить корректное предложение LLM. Она
не разрешает побочный эффект и не доказывает качество ответа.

## Примеры

### Матрица совместимости

Текущий шаг требует `search_evidence`, `propose_patch`, изображение на входе,
строгую схему `change_plan/v1` в совместимом диалекте, потоковую выдачу,
входной context объёмом `52k`, резерв ответа `4k` и версионированную возможность
`reasoning_budget:v1`.

| Требование | Основной A | Резервный B | Дешёвый C |
|---|---:|---:|---:|
| Tool `{search_evidence, propose_patch}` | оба | оба | только `search_evidence` |
| Строгая схема `change_plan/v1` | да | да | JSON без гарантии схемы |
| Вход `{text, image}` | да | да | только текст |
| Входной context `52k` | `128k` | `64k` | `128k` |
| Резерв ответа `4k` | до `16k` | до `8k` | до `16k` |
| Потоковая выдача | да | да | да |
| `reasoning_budget:v1` | да | да | нет |
| Результат | совместим | совместим | четыре несоответствия |

Если A возвращает `503` до первого события и его контракт исключает побочный
эффект на стороне сервера, политика выбирает B. Низкая цена не делает C
допустимым. Если B отсутствует, маршрутизатор возвращает
`NoCompatibleRoute` с четырьмя причинами и не вызывает несовместимый клиент.
Если состояние эффекта A неизвестно, Agent ожидает сверки вместо
автоматического перехода к B.

### Небольшой набросок, независимый от поставщика

Это форма будущего контракта, а не реализация практики:

```python
@dataclass(frozen=True, slots=True)
class SchemaRequirements:
    mode: str
    dialect: str
    keywords: frozenset[str]


@dataclass(frozen=True, slots=True)
class CapabilityRequirements:
    tools: frozenset[str]
    input_modalities: frozenset[str]
    output_modalities: frozenset[str]
    schema: SchemaRequirements
    min_input_tokens: int
    min_output_tokens: int
    stream_mode: str
    experimental: frozenset[str]
    allowed_maturity: frozenset[str]


def select(routes, required):
    checks = tuple(check(route.profile, required) for route in routes)
    compatible = [
        route
        for route, report in zip(routes, checks, strict=True)
        if not report.gaps
    ]
    if not compatible:
        raise NoCompatibleRoute(checks)
    return rank(compatible)[0]
```

Важен порядок операций: `check → filter → rank`. Конструкция
`rank(all_routes)[0] → strip_unsupported_fields` принципиально неверна.

### Журнал выбора маршрута

```text
requirements_revision=change-plan/v1
registry_revision=2026-08-12.3
candidate=primary-a     compatible=true
candidate=fallback-b    compatible=true
candidate=cheap-c       gaps=tool,strict_schema,image,experimental
selected=fallback-b     reason=primary_effect_free_failure_before_first_event
```

Журнал нужен для разбора инцидента и воспроизведения решения. Он фиксирует
факты выбора, но не обязан содержать prompt или конфиденциальные аргументы tool.

## Заметки и наблюдения

### Связь с текущим кодом

- [`ModelRequest.tools`](../../lessons/module_01_provider_contract/implementation/contracts.py)
  и `JsonSchemaFormat` уже выражают часть требований.
- `InputMessage.content` пока содержит только `str`; типы входных и выходных
  данных отдельно не моделируются.
- `ModelClient.complete()` и `stream()` означают один запрос к поставщику.
  Наличие `stream()` в `Protocol` не доказывает поддержку потоковой выдачи
  конкретным маршрутом.
- `UnsupportedCapability` защищает границу адаптера, когда поставщик фактически
  отклоняет запрос. Для отказа по нескольким маршрутам дополнительно нужен
  `NoCompatibleRoute` с отчётами по всем кандидатам.
- `StreamingRuntime` темы 1.3 ограниченно повторяет запрос к тому же клиенту
  после раннего `429`; это не переключение между LLM. Новый маршрутизатор
  должен наследовать исходный общий крайний срок.

Новые типы возможностей лучше добавлять в отдельный урок, не меняя поля
`ModelRequest`: текущие темы и контрактные тесты зависят от него. До выбора
маршрута нужен независимый шаблон; затем для каждой попытки строится новый
`ModelRequest` с LLM выбранного маршрута и неизменными `messages`, `tools`,
`response_format` и идентификатором запроса приложения.

### Реестр — проверенное описание, а не вечная истина

Способы получения сведений у поставщиков различаются. OpenAI Models API отдаёт
базовые метаданные идентичности, а сравнение возможностей опубликовано в
отдельном каталоге. Anthropic Models API включает больше метаданных
возможностей. Gemini Models API публикует ограничения по токенам и доступные
способы генерации, но не весь контракт маршрутизации. Поэтому промышленный
реестр объединяет версионированное описание, первичную документацию, настройки
учётной записи и региона, а также контролируемые проверки.

Профиль должен хранить `source`, `observed_at`, используемый вариант API,
`snapshot`, `alias`, регион и права учётной записи. Устаревший профиль всё
равно может ошибиться, поэтому адаптер сохраняет защитную ошибку
`UnsupportedCapability` и обновляет телеметрию.

### Чего совместимость не доказывает

- качество, фактическую и смысловую корректность результата — это проверяет
  оценка качества;
- доступность прямо сейчас — это сигнал работоспособности и квоты;
- полномочия арендатора и размещение данных — это проверяет политика доступа;
- корректность конкретного предложения вызвать tool — это проверяют схема и
  бизнес-правила;
- право выполнить побочный эффект — это отдельная граница полномочий.

Эти оси участвуют в допуске маршрута или его ранжировании, но не должны
смешиваться в один непрозрачный признак `supports_request=True`.

### Ограничения будущей практики

- Начальный реестр будет статическим и детерминированным, без обращения к
  реальному API поставщика.
- Поля context будут задавать минимальные входной бюджет и резерв ответа, а не
  заменять полноценный токенизатор и точную оценку prompt.
- Идентификация tool начнётся с имени; версия и отпечаток схемы появятся в
  модуле про протокол tool.
- Простая модель сочетаний возможностей не покроет все ограничения
  поставщиков.
- Тесты свойств докажут инварианты маршрутизации на искусственных профилях, но
  не реальные права учётной записи и не качество LLM.

## Итоги

Маршрутизация с учётом возможностей отделяет доступность от смыслового
искажения. Реестр хранит версионированные факты, проверка совместимости
отказывает при неопределённости, политика ранжирования выбирает только среди
подходящих вариантов, а адаптер выполняет один запрос к поставщику.
Несовместимый резервный маршрут не становится допустимым из-за низкой цены или
хорошей работоспособности. Любое ослабление требований — отдельное решение
приложения с новым состоянием Agent и записью аудита.

После команды `к практике` реализуем механизм с нуля: неизменяемый реестр без
`if model_name`, типизированные отчёты о совместимости, маршрутизатор с отказом
при неопределённости и детерминированные тесты свойств. Фреймворк на этой
стадии не нужен.

## Источники

по спецификации OpenAPI `2.3.0`, Anthropic API с обязательным
`anthropic-version: 2023-06-01`, Gemini API `v1` и используемым SDK по
умолчанию `v1beta`. Ссылки фиксируют источники выводов, а псевдонимы LLM
считаются изменяемыми.
